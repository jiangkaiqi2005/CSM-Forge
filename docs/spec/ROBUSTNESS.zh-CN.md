# 游玩期鲁棒性、恢复、检查点与运维

规范版本：2.0-design。关联需求：F-REC-01、F-REC-02、F-REC-03、F-SAVE-01、F-FAIL-01、F-LOAD-01、F-LIVE-01、F-OBS-01、F-UX-01。新增策略均需实现与实机验证。

## 1. 故障隔离原则

鲁棒性是“错误不污染已确认城市、正常玩家尽量继续、资源有界且可定位恢复”，不是无限吞异常、不停重试或强制让所有人等最慢客户端。

故障影响范围按真实性决定：报文错误属于连接；下载失败属于 Transfer；客户端投影损坏属于该副本；Host 世界部分修改或提交链不可信才属于房间。仅凭异常类型不能决定作用域：同一个 IOException 可能是可重试临时下载，也可能是检查点发布失败。

## 2. 故障决策矩阵

| 情况 | 状态/处理 | 正常玩家 | 重试与退出 |
| --- | --- | --- | --- |
| 未认证、伪造身份、错误阶段消息 | 拒绝或关闭该连接，不进入世界层 | 继续 | 不自动升级权限 |
| 无效 Intent、过期读集、资源不足 | 稳定 Rejected Receipt，世界未改变 | 继续 | 玩家重新选择后新操作 |
| 尚未执行时队列已满 | Busy/RetryAfter，不能提前显示成功 | 继续，必要时限流 | 有界等待，不自动无限入队 |
| 可丢弃表现包迟到/乱序 | 按 generation/sequence 丢弃 | 继续 | 等下一帧，不重同步城市 |
| 持久结果缺口且日志仍覆盖 | 该 Client 只读 CatchingUp，补连续日志 | 继续 | 超出保留窗口转新快照 |
| 相同 Revision 不同摘要 | 隔离该 Client 并保存首次分叉 | 继续 | 一次自动完整恢复，重复则断开 |
| 客户端 Apply 部分失败 | 撤销编辑、旧 LoadGeneration；完整重载 | 继续 | 不清标志后继续应用 |
| 块损坏/缺块 | 本 Transfer 请求有限重传、整文件再校验 | 继续 | 冲突摘要/超限关闭本 Transfer |
| 下载/加载取消 | 本 Join 终止，释放引用/租约/句柄 | 继续 | 新尝试必须新代次 |
| 慢客户端持续追不上 | 减少表现，限额追赶，再基线或断开 | 继续，不等它 | 不无限 pin 日志；只读也有期限 |
| Host 模拟暂时卡顿，网络还通 | 标记 HostStalled，客户端禁止新的持久编辑 | 已确认画面可保留 | 不把网络心跳当模拟健康 |
| Host 原生/托管权威操作部分失败 | Fenced，停权威写入及新快照 | 全房停止修改 | 从此前有效检查点、新 Epoch 恢复 |
| 检查点磁盘满/发布失败 | 不发布新 checkpoint，保留旧检查点，显示未保存状态 | 世界未污染时可继续 | 不承诺新操作已落盘；禁需新基线的加入 |
| 房间目录/信令暂时不可用 | 禁新加入/换路所需操作；已建立端到端连接不主动拆除 | 直连可继续 | 到必要认证/路由期限再按策略断开 |
| 中继断开 | 新连接绑定重建路径并恢复 | 其他不受影响连接继续 | 不能对未确认意图盲重发 |
| 游戏进程崩溃/系统重启 | 运行实例终止，无法由 finally 修复 | 全房断开 | 重启后校验旧检查点，新 Epoch |
| 运行中 Mod/Schema/游戏签名改变 | 撤销不再满足的能力，必要时关房 | 不假装仍兼容 | 保存可信状态、退出后重新协商 |

自动恢复默认一次完整重载；五分钟内再次同类语义不同步即停止自动循环，提示诊断和重新开房。连接重试可以另有短指数退避和随机抖动，但不得复用失败 JoinContext。数字来自待测预算，不是已测结果。

## 3. 四种健康信号必须分开

NetworkAlive：认证连接有合法活动；HostProgress：权威模拟边界/提交序列正常推进或明确暂停；ReplicaProgress：Client 实际应用进展；LoadProgress：当前阶段确有下载、校验、读取或游戏加载工作进展。

暂停的城市不应因没有新 Commit 被判定死亡，但仍需网络和明确的世界暂停状态。网络工作者活着而模拟线程卡死时，不能通过持续心跳永久显示“健康”。下载完但 OnLevelLoaded 卡住，也不能用收到心跳重置无限加载等待。

所有间隔由接收者本地单调时钟计算。远端墙钟只作诊断，不用于租约是否失效、重试序号或当前世界归属。超时状态不自动因一个迟到心跳恢复 Live；重新健康也必须核对复制进展与有效授权。

假设配置的网络 degraded/expired 阈值为 6/20 秒：超过 degraded 即撤销新编辑并显示连接异常；超过 expired 结束绑定，后续重连走认证/恢复。游戏加载有独立进度停滞和总时限，不能沿用普通心跳阈值误杀正常加载。阈值仅在批准的性能配置内提供有界检测，不等于对任意网络延迟的保证。

## 4. 恢复状态与不确定操作

Client：Live → Degraded/CatchingUp → RecoveryPending → Loading → CatchingUp → AwaitingActivation → Live；明确拒绝/超时后 Closed。期间镜头可观察最后已确认画面，但界面标明非实时，不允许当地继续积累正式修改。

恢复先记录证据并撤销 Grant，再取消旧任务。优先补已确认 AppliedRevision 后的连续日志；当真实游戏状态不再可信时，不允许只从旧 Revision 续放，必须重新安装整个可信闭包。首版闭包是整份 Client 世界。

断线之前发送过的操作可能已经在 Host 完成。OperationLedger 的查账结果是重试依据；Timeout 不等于 Rejected。UI 状态分为待发送、Host 已接受/提交、本地已显示、检查点已保存和结果未知。只把最后一个阶段画成“已安全存档”是错误的。

任何自动恢复都不能把 Client 投影保存成主机恢复来源。需要给用户另存本地副本时必须独立标识非权威，不覆盖原城市或正式检查点。

## 5. 检查点格式和发布流程

CheckpointManifest 至少包含 CheckpointId、WorldId、Epoch、基线 Revision/Tick、游戏 build、领域/协议/Checkpoint Schema、内容与 Mod 支持目录摘要、每个文件长度和哈希、领域根、逻辑实体映射/代次、纳入检查点的操作账本高水位及前一有效检查点 ID。

原生 `.crp`、Forge 状态、映射和元数据必须属于同一个一致切面；文件完整性摘要与语义状态根分开。不能在游戏保存结束时随手写上“当前 Revision”，因为保存可能从更早时刻开始。实际冻结的 B 才是基线。

发布顺序：在应用管理目录创建唯一临时检查点 → 写入已冻结内容 → 刷盘并校验全部文件 → 写 manifest 并刷盘 → 同文件系统发布到唯一 sealed 目录 → 原子替换 latest 指针 → 保留前一有效检查点。具体 Flush/Replace/目录持久化语义由平台适配器验证，不能声称普通 Stream.Flush 已覆盖断电持久性。

latest 指针损坏或丢失时，只扫描 sealed 候选并校验完整 manifest、关联文件和支持信息；选择可证明完整的最近检查点。半份临时目录、只写了 .crp 的目录和哈希不匹配的目录不参与恢复。文件时间戳不能单独决定哪个是有效世界。

不得原地覆盖用户原始存档，不使用远端传来的路径，不自动安装或替换游戏 DLL。原生加载失败保留旧检查点，清理本次 Client 临时世界；保存失败不是世界回滚。

## 6. Host 崩溃、权限与纪元

只承诺从有效检查点恢复。主机内存日志不自动等于可崩溃重放的整个模拟；只有完整、经过校验且具备必要状态/操作账本的持久日志适配通过验收后，才可以扩展恢复点。

恢复采用新随机非零 Epoch 或其他经过持久化验证的唯一实例标识，禁止每次启动都用常数 1。旧连接、Grant、Barrier、Transfer 和未完成操作全部失效。恢复界面显示最后检查点及可能丢失的之后操作，不宣称跨崩溃 durable exactly-once。

首版不自动选新 Host，不在断网分区中允许两端都继续创建权威城市，不自动合并两份分叉存档。旧 Host 活着也必须显式关闭旧房间后再以有效检查点重开；发现错误 Epoch 直接拒绝。

## 7. 资源预算与背压

统一提议预算在 [budgets.json](budgets.json)。这些数值是验收起点，尚未改动 M0 `Limits`，也没有经过真实城市测量。

同时控制单 Peer 与房间总量：认证连接数、进行中加入、快照读取/下载窗口、磁盘暂存、历史日志、保留根、解码大小、游戏待应用队列、每帧/每 tick 工作和日志文件。

快照最多 512 MiB、块 32 KiB、最多 16384 块，是 v2 设计目标；当前 M0 仍是 64 MiB/8192 块限制。增加上限时必须改流式 API，而不是把几份 512 MiB byte[] 塞进旧 Mono。房间镜像本体与插件额外复制开销分别测量；共享快照应复用磁盘文件和不可变页，不以“共享”名义共享可变读取游标。

活跃状态队列达到高水位先限制该 Peer 的表现和新操作；继续积压则独立恢复/断开。全房背压不能卡在模拟线程同步等待发送。日志达到房间上限时撤销滞后租约、暂停新加入；若连活跃 Client 基本复制也长期无法满足，明确缩小支持规模/速度，不丢持久结果。

长任务可在纯准备阶段分块调度；已经修改引擎的不可逆阶段超时不能靠 Thread.Abort 强行截断。超预算只用于暂停后续工作和记录故障，如何回到可信状态按适配器恢复契约处理。

## 8. 校验频率与局部修复

持续维护增量根和 AppliedRevision；按固定发布边界抽查实际投影；低频完整审计使用不可变页或一致安全点。不同 tick/Revision 的散乱扫描只标记为不可比较，不升级成确定 desync。

首个确定不一致记录 Root/Domain/Partition/Revision 和前后有限操作。若根不存在、Schema 不同或旧样本已淘汰，明确报告原因，不用全零根参与比较。

局部修复必须由适配器声明依赖闭包，停止闭包内读写，安装目标版本、重建派生结构并验证与其他域边界；未证明这些条件时完整 Client 重载。默认不做每几秒覆盖资金来掩盖持续漂移。

## 9. 日志和诊断包

结构化事件至少含：时间源、World/Epoch、Member/Connection、Join/Transfer/LoadGeneration、Operation/Batch、Revision/Tick、Domain/Partition、Barrier/Grant、状态迁移、故障码、期望/实际摘要、队列字节、延迟和执行耗时。

事件名区分 WireReceived、Authenticated、Queued、IntentRejected、AuthorityCommitted、ReplicaStaged、GamePublished、AppliedAcked、CheckpointPublished。捕获失败应保留错误类别和经过安全处理的堆栈；不把任意网络文本拼进日志。

诊断环与 JSONL 轮转有上限。首次分叉以单个 incident ID 保存，后续相同错误计数聚合，避免日志风暴。用户主动导出脱敏包：构建/Mod 指纹、状态机、有限事件、性能分位数和可复现种子；默认不含城市文件、认证票据、邀请码、网络密钥、私人绝对路径或完整原始报文。

运营指标包括并行加入成功率、各阶段耗时、追赶速率/落后量、重基线次数、恢复成功率、Host Fenced 次数、日志淘汰原因、资源高水位、主线程/模拟线程开销和持续运行内存趋势。指标必须注明硬件/城市/Mod/网络配置，不能脱离条件引用一个平均值。

## 10. 玩家体验与回退

开房先检查支持范围、原始存档备份/检查点能力、端口/连接与内容差异；展示当前产品支持模式和最大人数。加入界面分别展示下载、校验、加载、追赶和等待激活；下载字节达到 100% 不显示“已进入城市”。

玩家可随时取消。单个加入者失败时 Host 看到该玩家状态，不弹全房阻塞对话框。掉线期间工具禁用但相机可用；恢复结束再显示 Live。反复失败时提供退出、重新加入和导出诊断，而不是无限转圈。

未经验证的新适配器默认关闭。回退发布需要检查协议/检查点可读性，保留旧文件；不能让旧程序直接写新 Schema 存档。恢复数据优先于 UI 便利，不以自动转换覆盖用户唯一存档。

## 11. 实机门槛与剩余风险

网络/托管异常的隔离可以自动化验证，原生库崩溃、游戏线程死锁、未知第三方代码和电源故障仍需要独立测试。并行加入不会凭空解决 CPU/带宽不足或不完整的游戏状态闭包。当前文档定义了处理机制和验收输入，没有宣称已经完成真实弱网络、24 小时游戏或崩溃恢复测试。
